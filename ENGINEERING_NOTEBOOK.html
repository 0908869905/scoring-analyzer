FRC Scoring Analyzer — 工程筆記

隊伍軟體組 ｜ 2026 賽季
專案：比賽影片自動進球偵測分析工具

1. 專案背景

為什麼要做這個？

今年賽季開始後，我們發現一個問題：每次看完比賽影片，大家對「誰進了幾球」都各有各的說法。手動計數很容易看漏，尤其 Teleop 階段 6 台機器人在場上跑來跑去，球飛來飛去，靠人眼真的不太行。

搜了一圈現成工具，FRC scouting app 全都是手動記錄的。我們想要的是：丟一個比賽影片進去，自動告訴我每台機器人進了幾球、命中率多少。所以決定自己寫。

競品調查

Chief Delphi 上找到 Team 5951 做過影片分析系統（YOLO 偵測球和機器人），但綁定特定賽季模型、需要大量標註資料。我們想做更通用的版本——盡量不依賴每年重訓的模型。

技術選型

方案優點缺點結論
全用 YOLO AI精確度高需大量標註、每年重訓太重
全用 HSV 色彩過濾簡單、免訓練受燈光影響球偵測可以，機器人不夠
HSV + AI 混合取兩者長處系統較複雜採用

最後決定：球偵測用 HSV（黃色球顏色鮮豔，過濾就夠）、機器人偵測用 HSV Bumper 為主 + YOLO 備選、GUI 用 CustomTkinter（Python 生態熟悉、暗色主題看影片舒服）。

2. 系統架構

使用者介面（主視窗 + 設定面板）
　　↓
分析管線（逐幀處理）
　├─ 球偵測（HSV 色彩過濾 / AI 備用）→ 球追蹤（質心匹配）
　├─ 機器人偵測（HSV Bumper / YOLO）→ 機器人追蹤（距離匹配 + Re-ID）
　├─ 背景模型（自動前景分離）
　└─ 進球判定 + 射手歸因 + 出手偵測
　　↓
輸出：得分統計表 / 進球事件時間軸 / CSV 匯出

每一幀的處理流程：

讀取影片幀 → 裁切分析區域 → 背景遮罩（觀眾席變黑）→ 球偵測（找黃色物體）→ 球追蹤（連接同一顆球）→ 機器人偵測（找紅藍 Bumper）→ 機器人追蹤（辨識是哪台）→ 進球判定 → 記錄事件

3. 球偵測

HSV 色彩過濾（採用方案）

FRC 的球是亮黃色的，在 HSV 色彩空間裡很容易跟背景分開。

處理流程：
原始影像 → 高斯模糊（消除運動模糊）→ 轉 HSV → 黃色範圍過濾 → Close 形態學 7×7（把碎裂的球補成整塊）→ Open 形態學 3×3（去小噪點）→ 找輪廓 → 面積過濾 → 輸出球位置
踩坑：形態學順序寫反了（先 Open 再 Close），球偵測直接壞掉。原因是球的色彩 mask 本身有洞，先 Open 會把碎片全刪掉，Close 也救不回來。改成先 Close 再 Open 之後恢復正常。

GPU 加速：4K 影片很大，我們用 OpenCV 的 UMat（OpenCL）把五個影像處理步驟全丟到 GPU 上跑，最後才把結果拉回 CPU。整個管線只有一次上傳和一次下載。

AI 模式（試過但放棄了）

也試過 YOLO 做球偵測，近距離效果不錯（信心值 0.67），但遠距離完全不行。原因：訓練資料是近距離球特寫，比賽影片是廣角遠景，球只有十幾像素。後來決定球偵測就用 HSV——黃色球在任何距離都是黃色的。

HSV 自動校正

每個場地燈光不同，HSV 參數也要跟著調。我們做了自動校正：用戶在影片上點幾下球的位置，系統用 K-Means 分離球色 vs 背景，再用百分位法自動算出 HSV 範圍。比手動調 slider 快很多。

4. 機器人偵測

這塊改了好幾版，是整個專案花最多力氣的部分。

第一版：YOLO 偵測

用 Roboflow 的 Main Robot Detection 資料集（1,172 張，Red / Blue 兩類），在 Google Colab 免費 T4 GPU 上訓練 YOLOv11n，約 30 分鐘練完，匯出 ONNX（10.1 MB）。

踩坑 1 — 資料集選錯：一開始選了 WorBots 4145 資料集（3,291 張），但類別超雜，模型把記分板、音箱都框成「機器人」。改成只有 Red/Blue 兩類的資料集後解決。
踩坑 2 — 類別名稱不相容：換資料集後偵測器零輸出。查了半天發現過濾函式只認 "red_robot"，新資料集叫 "Red"，全被過濾掉了。教訓：換資料集要同步檢查類別名稱相容性。

第二版：HSV Bumper 偵測（現在的預設）

Bumper（防撞條）每年都有，而且一定是紅色或藍色（FRC 規則規定）。所以做了 HSV 偵測器找紅藍矩形色塊。

處理流程：
模糊 + HSV 轉換 → 紅色過濾（兩段範圍，處理 Hue 環繞）→ 藍色過濾 → 合併 → 矩形核形態學（Bumper 是扁的）→ 輪廓偵測 → 面積 + 長寬比過濾 → NMS 去重 → 模板匹配過濾（可選）
設計細節：紅色在 HSV 裡 Hue 值跨越 0 度（會環繞），必須做兩次過濾再合併。形態學用矩形核（9×5）而非正方形，因為 Bumper 是水平長條形。

Bumper 模板匹配：用戶可以在影片上點幾下機器人的 Bumper，系統建立 HSV 直方圖模板，分析時只保留跟模板相似的偵測結果，過濾掉觀眾衣服、標示牌等假陽性。

5. 多目標追蹤（MOT）

ByteTrack 的失敗

這是我們最大的一次踩坑。ByteTrack 用 IoU（框的重疊面積）來配對前後幀的偵測結果，一般場景很好用，但在我們這裡完全失效。

原因：4K 影片裡機器人的框只有約 25 像素，但每幀移動 30~50 像素。框的位移比框本身還大，前後幀完全不重疊，IoU 永遠是 0，配對全失敗。1200 幀裡只成功配對 11 次（覆蓋率 5.4%）。

我們的解法：距離匹配

改用距離來配對。同一台機器人在連續幀之間位置不會差太遠。

匹配流程：
1. 每台已追蹤的機器人，用速度預測下一幀位置
2. 計算所有「預測位置 ↔ 偵測結果」的距離
3. 加入顏色直方圖 Re-ID：外觀不像的候選距離會被拉遠
4. 全域最短距離優先，貪心配對
5. 距離超過閾值的不配對（視為新目標）

修復前後對比

指標ByteTrack（IoU）距離匹配（修復後）
機器人偵測次數111,000
插值後涵蓋幀數114,521
幀覆蓋率5.4%100%
Blue 機器人追蹤0 台5 台
關鍵教訓：不要假設現成演算法一定適用自己的場景。ByteTrack 在一般監控影片上很好用，但在 4K 高速小目標場景完全不行。

後處理 Label 合併

機器人被遮擋後重新出現會被分配新 ID。分析完成後做後處理：同聯盟、時間不重疊、位置接近的 label 自動合併。Red 的 label 數從 7 個降到接近預期的 3 個。

6. 進球判定與射手歸因

進球判定

用戶在影片上標記 Hub 位置（多邊形），分析時每幀用 Ray Casting 射線法檢查球是否在多邊形內。球要在 Hub 裡待滿 3 幀才算進球，進球後 10 幀冷卻避免重複計數。

三層射手歸因

優先順序方法說明
第一層HP 線段歸因球軌跡靠近人類玩家投射線 → 自動進球，不需機器人
第二層球所有權歸因追蹤每顆球「屬於」哪台機器人，球被射出時的 owner = 射手。球在空中時鎖定 owner 不變
第三層鄰近歸因（兜底）回溯進球前 0.5 秒，找 500px 內最近的機器人

射手重新歸因

第一次歸因只成功 7%（42 球歸因到 3 球），因為進球那一幀機器人可能沒被偵測到。加了後處理步驟：用合併 + 插值後的完整軌跡重新匹配射手。

結果：射手歸因率 7% → 47%。改善明顯但仍有提升空間。

出手偵測

找球速度突增的點（球被打出的瞬間）+ 球往上飛 + 附近有機器人 → 判定為出手。追蹤球後續是否進 Hub：進了 = goal，沒進 = miss。有了這個就能算命中率。

7. 背景模型

比賽影片裡觀眾席、計分板的顏色會干擾偵測。一開始用手動畫多邊形遮罩，但每換影片都要重畫，很麻煩。

Temporal Median 自動背景

原理：場地和觀眾席是不動的，機器人和球是快速移動的。

1. 從影片均勻取 50 幀
2. 每個像素位置取中位數 → 得到一張「乾淨的背景圖」
3. 分析時：每幀減去背景圖，差異大的地方 = 前景（機器人和球）
4. 背景區域設為黑色，偵測器只看前景
為什麼用中位數？中位數對離群值穩健。如果某幾幀剛好有機器人停在某處，平均數會被拉偏，中位數不會。效果比手動畫遮罩好太多了。

10. 反思與未解問題

學到的教訓

  1. 不要假設現成演算法一定適用 — ByteTrack 在 4K 小目標場景完全失效，自己寫距離匹配反而更好
  2. 訓練資料要跟實際場景一致 — 近距離球特寫訓練出來的模型，遠距離完全不認識球
  3. 參數要隨解析度調整 — 4K 下的面積閾值、距離閾值跟 1080p 差很多
  4. 簡單方法有時候比複雜方法穩 — HSV 色彩過濾比 AI 模型更適合球偵測

目前未解的問題

  • HSV Bumper 模式在實際影片上偵測不穩定，機器人追蹤仍會失效
  • 射手歸因率 47% 還不夠高，目標 70%+
  • 不同場地的參數差異大，自動適配還沒做好
