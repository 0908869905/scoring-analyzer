## 1. 專案背景與動機

### 為什麼要做這個東西？

今年賽季（2026 Rebuilt）開始後，我們隊上討論到一個問題：每次看完比賽影片，大家對「誰進了幾球」都各有各的說法。手動計數很容易看漏，尤其是快節奏的 Teleop 階段，6 台機器人在場上跑來跑去，球飛來飛去，靠人眼真的不太可靠。

我們本來想找現成的工具，但搜了一圈沒有什麼好用的。市面上的 FRC scouting app（像 ScoutingPASS、The Blue Alliance 等）都是**手動記錄**的，需要人在現場即時點按鈕。我們想要的是：**丟一個比賽影片進去，自動告訴我每台機器人進了幾球、命中率多少**。

所以我們決定自己寫一個。

### 競品調查

我們去找了其他隊伍有沒有做類似的東西。在 Chief Delphi 上找到 Team 5951（Makers Assemble）做過一個比賽影片分析系統，他們用 YOLO 偵測球和機器人，然後追蹤進球。不過他們的方案是建立在特定賽季的模型上，而且需要很多標註資料。

看完之後我們覺得，他們的方向是對的，但我們想做一個更「通用」的版本——不需要每年重新訓練模型，最好用色彩偵測就能搞定大部分場景。

### 技術選型過程

一開始我們想過幾個方案：

| 方案 | 優點 | 缺點 | 結論 |
|------|------|------|------|
| 全用 YOLO AI | 精確度高 | 需要大量標註資料、每年要重新訓練 | 太重了 |
| 全用 HSV 色彩過濾 | 簡單、不需訓練 | 容易受燈光影響 | 球偵測可以，但機器人不行 |
| HSV + AI 混合 | 取兩者優點 | 系統複雜度高 | **最後選這個** |

最後決定：
- **球偵測用 HSV**——FRC 的球顏色很鮮豔（黃色），HSV 過濾就夠了
- **機器人偵測用 HSV Bumper + YOLO 備選**——先試 bumper 色彩偵測（紅藍都很明顯），不行再上 YOLO
- **GUI 用 CustomTkinter**——Python 生態熟悉，暗色主題看影片比較舒服

## 2. 需求分析

### 核心功能需求

我們列了一下這個工具最少要做到什麼：

1. **載入比賽影片**——支援各種格式（MOV、MP4），4K 60fps 也要能處理
2. **偵測球的位置**——每一幀都要知道球在哪
3. **追蹤球的軌跡**——同一顆球在不同幀之間要連起來
4. **偵測機器人位置**——知道 6 台機器人分別在哪
5. **追蹤機器人身份**——Red-1 不能跟 Red-2 搞混
6. **判定進球**——球進入 Hub 區域就算進球
7. **歸因射手**——這球是哪台機器人射的？
8. **統計命中率**——每台機器人的出手次數和進球率

### 額外需求（後來發現很重要的）

做著做著才發現有些東西不做不行：

- **背景過濾**——觀眾席和計分板的顏色會干擾偵測，必須排除
- **HSV 校正**——每個場地燈光不同，HSV 參數要能調
- **播放速度控制**——分析完要能回看，1~5 倍速
- **Debug 視圖**——出問題時要能看到偵測的中間步驟

## 3. 系統設計

### 架構圖

我們把系統拆成幾個主要模組：

```
使用者介面 (app.py + settings_window.py)
     |
     v
分析管線 ─── 球偵測 (detection.py) ──── 球追蹤 (tracking.py)
     |
     ├─── 機器人偵測 (robot_detection.py) ──── 機器人追蹤 (robot_tracker.py)
     |
     ├─── 背景模型 (background.py)
     |
     └─── 進球判定 + 歸因 (scoring.py)

基礎設施 ─── 參數管理 (config.py + runtime_config.py)
     |
     ├─── 幾何工具 (geometry.py)
     |
     ├─── HSV 校正 (calibration.py)
     |
     └─── 模型檔案 (models/*.onnx)
```

### 資料流

每一幀的處理流程大概是這樣：

```
讀取影片幀
  → 裁切到分析區域（如果有設的話）
  → 背景遮罩（把觀眾席變黑）
  → 球偵測（找黃色的東西）
  → 球追蹤（這顆球上一幀在哪？）
  → 機器人偵測（找紅藍 bumper）
  → 機器人追蹤（這台機器人是 Red-1 還是 Red-2？）
  → 進球判定（球有沒有進 Hub？）
  → 記錄事件
```

### 為什麼選 Python + CustomTkinter？

老實說，Python 做影像處理不是最快的選擇。但我們考慮到：
1. 隊上大家比較熟 Python
2. OpenCV 的 Python binding 很完整
3. ONNX Runtime 有 Python 版
4. 不需要即時處理（可以慢慢分析），速度不是最大瓶頸

CustomTkinter 是因為它的暗色主題很好看，而且是 Tkinter 的延伸，不用額外學太多新東西。

## 4. 球偵測模組

### 4.1 HSV 色彩過濾（最後採用的方案）

這是我們花最多時間調的模組之一。原理很簡單：FRC 的球（Cargo / Note）是亮黃色的，在 HSV 色彩空間裡很容易和背景分開。

**處理流程：**

```
原始影像 (BGR)
  → GaussianBlur(5,5)     ← 消除運動模糊造成的色彩碎裂
  → 轉 HSV 色彩空間
  → inRange(黃色範圍)      ← 只留下黃色像素
  → Close 形態學(7x7)      ← 把破碎的球 mask 補成整塊
  → Open 形態學(3x3)       ← 去掉小噪點
  → findContours           ← 找輪廓
  → 面積過濾               ← 太小的不是球，太大的也不是
  → 回傳球的位置 (cx, cy)
```

**為什麼 Close 要在 Open 前面？**

這個我們踩過坑。一開始寫反了（先 Open 再 Close），結果球偵測直接壞掉。原因是：球的 HSV mask 本身就有很多小洞（特別是有運動模糊的時候），如果先做 Open（去噪），會把這些小碎片全部刪掉，之後再 Close 也救不回來。

改成先 Close（補洞）再 Open（去噪）之後，效果好很多。Close 的 7x7 核比較大，可以把離散的色塊接起來；Open 的 3x3 核比較小，只去掉真正的小噪點。

**GPU 加速：**

4K 影片很大（3840x2160），逐幀做 HSV 過濾 CPU 會很吃力。我們用了 OpenCV 的 UMat（OpenCL 加速），把影像丟到 GPU 上做模糊、色彩轉換、inRange、形態學這幾步，最後才把結果拉回 CPU 做 findContours（因為 findContours 不支援 UMat）。

```python
if cv2.ocl.haveOpenCL():
    src = cv2.UMat(frame)  # 影像上傳 GPU
    blurred = cv2.GaussianBlur(src, (5, 5), 0)  # GPU 上執行
    # ... 後續操作都在 GPU
    mask = mask_gpu.get()  # 只在最後拉回 CPU
```

好處是整個管線只有一次上傳和一次下載，五個 OpenCV 操作全在 GPU 跑完。

### 4.2 AI 模式（試過但放棄了）

我們也試過用 YOLO 做球偵測。從 Roboflow 找了一個 `fueldetection_grayscale` 的模型，轉成 ONNX 後可以本地推理。

**結果：近距離效果不錯（信心值 0.67），但遠距離完全不行。**

原因很單純：訓練資料全是近距離球的特寫照片，但比賽影片是從觀眾席拍的廣角鏡頭，球在畫面裡只有十幾個像素大。模型沒見過這種場景，當然偵測不到。

後來我們決定球偵測就用 HSV 了。黃色球在任何距離都是黃色的，HSV 不挑距離。AI 模式的程式碼還留著（`detection.py` 裡的 `FuelDetectorONNX`），但預設關閉。

### 4.3 HSV 自動校正

每個場地的燈光不一樣，所以 HSV 的黃色範圍也不一樣。我們做了一個校正功能：

**用法**：在影片上點幾下球的位置，系統會自動計算 HSV 範圍。

**背後原理**：
1. 用戶點擊的位置各取 40x40 像素的小區塊
2. 轉成 HSV，用 K-Means（k=2）把這些像素分成兩群（球 vs 背景）
3. 選飽和度高的那群（球的顏色比背景更飽和）
4. 用 5% 和 95% 百分位算 HSV 的上下限，加一點 margin

這比手動調 slider 快多了，而且用百分位而不是 min/max，可以過濾掉極端值。

## 5. 機器人偵測模組

這塊我們前前後後改了好幾版，是整個專案裡花最多力氣的部分。

### 5.1 第一版：YOLO ONNX 偵測

一開始我們打算用 YOLO 偵測機器人。找了 Roboflow 上的資料集，最後選了 Main Robot Detection（1,172 張，只有 Red 和 Blue 兩個類別，標註在機器人底盤上）。

在 Google Colab 上用免費的 T4 GPU 訓練了 YOLOv11n，大約 30 分鐘就練完了，匯出成 ONNX（10.1 MB）。

**踩坑紀錄 — 資料集選錯：**

一開始選了 WorBots 4145 的資料集（3,291 張），結果類別超雜：`red_robot`、`blue_robot`、`black_robot`、`note`、`speaker`、`display`。訓練出來的模型會把場地上的記分板、音箱都框出來當「機器人」。

改成 Main Robot Detection 之後乾淨多了。只有 Red 和 Blue 兩類，標註在底盤上（底盤是機器人最穩定可見的部分）。

**踩坑紀錄 — 類別名稱不相容：**

切換資料集之後，偵測器直接零輸出。查了半天才發現 `is_robot_class()` 這個過濾函式只認 `"red_robot"` 和 `"blue_robot"`，新資料集的類別叫 `"Red"` 和 `"Blue"`，全被當成「不是機器人」過濾掉了。

修好之後學到一個教訓：**換資料集一定要同步檢查類別名稱的相容性**。

### 5.2 第二版：HSV Bumper 偵測（現在的預設）

YOLO 需要訓練模型，每個賽季的機器人長不一樣就要重新練。但 bumper（防撞條）每年都有，而且一定是紅色或藍色的——這是 FRC 規則規定的。

所以我們做了一個 HSV 色彩偵測器，專門找紅色和藍色的矩形色塊：

```
原始影像
  → 模糊 + HSV 轉換
  → 紅色過濾（兩段 range，因為紅色 Hue 在 0 度附近會環繞）
  → 藍色過濾
  → 合併
  → Close 形態學（矩形核 9x5，因為 bumper 是扁的）
  → Open 形態學（矩形核 5x3）
  → 找輪廓
  → 面積過濾（太小的是噪點，太大的是背景）
  → 長寬比過濾（bumper 的寬高比大約 1.2~12）
  → NMS 去重
```

**紅色的坑：**

HSV 色彩空間裡，紅色的 Hue 值在 0 度附近。但 OpenCV 的 Hue 範圍是 0~180，所以紅色會出現在兩端：0~10 和 170~180。我們要做兩次 inRange 再 OR 起來：

```python
mask_red_1 = cv2.inRange(hsv, (0, 120, 80), (10, 255, 255))
mask_red_2 = cv2.inRange(hsv, (170, 120, 80), (180, 255, 255))
mask_red = mask_red_1 | mask_red_2
```

如果忘了做第二段，畫面偏暗的紅色 bumper 就會偵測不到。

**為什麼用矩形形態學核？**

Bumper 是水平的長條形，用正方形核做形態學會把垂直方向的噪點也接起來。改用 9x5 的矩形核之後，只有水平方向的色塊會被連接，效果好很多。

### 5.3 Bumper 模板匹配（進階過濾）

光靠顏色還不夠，場地上紅色和藍色的東西很多（標示牌、觀眾的衣服等等）。所以我們加了一個模板匹配機制：

1. 用戶在影片上點幾下機器人的 bumper
2. 系統從點擊位置取樣，建立 HSV 直方圖模板（H 和 S 通道，16x16 bins）
3. 分析時，每個偵測到的候選都要跟模板比對
4. 直方圖相似度太低的就丟掉

這樣可以篩掉大部分的假陽性。相似度閾值設在 0.3（Bhattacharyya distance），實測效果還行。

## 6. 多目標追蹤（MOT）

### 6.1 為什麼不能直接用 ByteTrack？

這是我們最大的一次踩坑。

ByteTrack 是一個很有名的 MOT 演算法，用 IoU（交集除以聯集）來關聯前後幀的偵測結果。一般場景下效果很好，但在我們的場景下**完全失效**。

**數據：** 1200 幀裡只配對成功 11 次，機器人幀覆蓋率 5.4%。

**原因：** 4K@60fps 影片裡，機器人的 bounding box 大約 25x25 像素，但每幀移動 30~50 像素。IoU 需要框有重疊才能匹配，但位移比框還大，根本不會重疊，IoU 永遠是 0。

```
幀 N:  [■] ← 機器人 bbox (25px)
           移動 40px →
幀 N+1:            [■]

兩個框完全不重疊 → IoU = 0 → ByteTrack 配對失敗
```

### 6.2 我們的解法：距離匹配

既然 IoU 不行，我們換成用**距離**來匹配。原理很簡單：同一台機器人在連續幀之間的位置不會差太遠。

```
1. 算距離矩陣 D[i][j] = 第 i 個追蹤目標到第 j 個偵測結果的距離
2. 全域最短優先，貪心分配
3. 距離超過閾值的不配對
```

**加上速度預測：**

單純用「上一幀的位置」算距離還是不夠好，因為機器人在高速移動。所以我們記錄每台機器人的速度 (vx, vy)，匹配時用**預測位置**而不是最後已知位置：

```
預測位置 = 上次位置 + 速度 × 幀間隔
距離 = |預測位置 - 偵測位置|
```

**加上顏色 Re-ID：**

有時候兩台同聯盟的機器人很近，光靠距離分不清。我們加了顏色直方圖來輔助：

```
每台機器人的 bbox 區域 → 提取 HSV 直方圖 (H+S, 16x16 bins)
→ 跟歷史直方圖比對 (Bhattacharyya similarity)
→ 加權距離 = 空間距離 × (1 + 0.4 × (1 - 顏色相似度))
```

顏色不像的候選會被「懲罰」，距離拉遠，降低配對優先度。

### 6.3 修復前後對比

| 指標 | ByteTrack (IoU) | 距離匹配 |
|------|-----------------|---------|
| 機器人偵測次數 | 11 | 1000 |
| 插值後涵蓋幀數 | 11 | 4521 |
| 幀覆蓋率 | 5.4% | 100% |
| Blue 機器人追蹤 | 0 台 | 5 台 |
| ID 穩定性 | POOR | FAIR |

### 6.4 後處理 Label 合併

距離匹配解決了大部分問題，但機器人被遮擋之後重新出現時，還是會被分配到新的 ID（例如 Red-1 消失後變成 Red-3）。

我們在分析完成後做後處理合併：
- 掃描所有同聯盟的 label
- 如果兩個 label 在時間上沒什麼重疊（< 15 幀），而且消失/出現的位置很近（< 800 像素）
- 就合併成同一個 label

這一步把 Red 的 label 數從 7 個降到了接近預期的 3 個。

## 7. 進球判定與射手歸因

### 7.1 進球判定邏輯

比賽影片裡，用戶先標記 Hub 的位置（多邊形，用左鍵放頂點、右鍵完成）。分析時，每一幀都檢查球是否在多邊形內。

多邊形判定用的是 **Ray Casting** 演算法（射線法）：從球的位置向右發射一條射線，數它跟多邊形邊界交了幾次。奇數次 = 在裡面，偶數次 = 在外面。

為了避免球剛好飄過 Hub 邊緣就被判進球，我們加了：
- **停留確認**：球要在 Hub 裡面待滿 3 幀（`SCORE_ZONE_DWELL_FRAMES=3`）才算
- **冷卻時間**：進球後 10 幀內不再判定（`SCORE_COOLDOWN_FRAMES=10`），避免重複計數

### 7.2 三層射手歸因

進球之後最重要的問題：這球是誰射的？

我們試了幾種方法，最後做成三層優先順序：

**第一層：HP 線段歸因（最高優先）**
如果球的軌跡靠近人類玩家（HP）的投射線段（< 300 像素），直接歸因給 HP。這種是自動進球，不需要機器人射。

**第二層：球所有權歸因**
我們追蹤每顆球在每一幀「屬於」哪台機器人（距離最近且 < 200 像素）。球被射出時，最後一個 owner 就是射手。

有個細節：球在空中飛的時候不應該換 owner（不然飛到另一台機器人旁邊就會被搶走），所以我們加了速度門檻——球速度 > 15 px/幀時鎖定 owner 不變。

**第三層：鄰近歸因（兜底）**
如果前兩層都找不到，就回溯進球前 0.5 秒，找 500 像素以內最近的機器人。

### 7.3 射手重新歸因

做完第一次歸因之後，我們發現成功率只有 7%（42 球只歸因到 3 球）。

原因是進球判定的那一幀，機器人可能剛好沒被偵測到（偵測器不是每幀都能偵測到所有機器人）。但分析跑完之後，我們有了完整的插值軌跡——每台機器人在每一幀都有位置（偵測到的是真實位置，沒偵測到的是插值出來的）。

所以我們加了一個 `reattribute_shooters()` 後處理步驟：用完整的合併+插值後軌跡重新匹配射手。

修復前後：射手歸因率 **7% → 47%**。雖然還不完美，但比一開始好太多了。

### 7.4 出手偵測

除了進球，我們也想知道「出手未進」的統計（用來算命中率）。

判定邏輯：
1. 掃描球軌跡，找速度突然變大的點（球被打出去的瞬間）
2. 同時球要是往上飛的（dy < 0，因為螢幕座標系 y 軸向下）
3. 附近要有機器人（不然可能只是球滾動）
4. 追蹤這顆球後續有沒有進 Hub：進了 = goal，沒進 = miss

有了出手偵測之後就能算命中率了：

```
命中率 = 進球數 / (進球數 + 未進數)
```

## 8. 背景模型與前景分離

### 8.1 為什麼需要背景過濾？

比賽影片裡，場地外面有很多東西會干擾偵測：
- 觀眾穿黃色衣服 → 被誤認為球
- 觀眾穿紅色/藍色衣服 → 被誤認為 bumper
- 計分板的紅藍色 → 被誤認為機器人
- LED 燈光變化 → 產生各種顏色雜訊

一開始我們做了一個手動場地遮罩：用戶在影片上畫一個多邊形把場地框起來，場地外面的像素直接忽略。但每次換影片都要重畫，而且場地形狀不規則，畫起來很麻煩。

### 8.2 Temporal Median 背景模型

後來我們想到一個更好的方法：自動建立背景圖。

原理是這樣的：比賽影片裡，場地、觀眾席、計分板這些東西是**不動的**（或者動得很慢），而機器人和球是**快速移動的**。如果我們取很多幀的「像素中位數」，移動的東西會被平均掉，留下來的就是靜止的背景。

```
1. 從影片均勻取 50 幀
2. 所有幀疊在一起，每個像素位置取中位數
3. 得到一張「乾淨的背景圖」（沒有機器人和球）

分析時：
4. 每一幀減掉背景圖 → 差異大的地方就是前景（機器人和球）
5. 差異 > 閾值(30) → 標記為前景
6. 膨脹一下補洞
7. 把背景區域設為黑色 → 偵測器只看前景
```

**為什麼用中位數而不是平均數？** 因為中位數對離群值更穩健。如果某幾幀剛好有機器人停在某個位置，平均數會被拉偏，但中位數不會。

效果比手動畫遮罩好太多了。觀眾席、計分板、場地外圍全部自動過濾，而且完全不需要手動操作。

## 9. 播放系統優化

### 9.1 4K HEVC 60fps 的挑戰

我們的測試影片是 4K (3840x2160) HEVC 60fps，檔案超大。一開始播放時卡到不行，後來量了一下發現兩個瓶頸：

1. **解碼慢**：OpenCV 解碼 HEVC 4K 只有 ~26fps，但影片是 60fps。連 1x 速度都不夠
2. **縮放慢**：用 LANCZOS4 把 4K 縮到顯示尺寸，每幀要 14ms

### 9.2 我們怎麼解的

**縮放換演算法：**
播放時從 LANCZOS4 換成 INTER_LINEAR。LANCZOS4 品質好但慢（14ms），LINEAR 快到只要 0.04ms，而且播放時每幀只顯示 33ms，肉眼根本看不出差別。暫停時才切回 LANCZOS4（暫停時用戶會仔細看畫面）。

**固定 30fps 顯示率 + grab() 跳幀：**
影片 60fps，但人眼覺得 30fps 就很流暢了。所以我們每次跳 2 幀（1x 速度時），只在目標幀才真正解碼。中間跳過的幀用 `cap.grab()`（只做解封裝，不解碼），比 `cap.read()` 快 35%。

**固定步進取代牆鐘同步：**
一開始用「牆鐘時間基準」（記錄開始播放的時間，算出現在應該在第幾幀），但渲染慢的時候會試圖追趕，跳很大步然後又卡住，觀感很差。

後來改成固定步進：每次 tick 前進 `fps/30 × speed` 幀。如果渲染來不及，播放速度就自動慢下來，但至少不會卡頓跳幀。

## 10. 測試與迭代

### 10.1 測試流程

我們的測試方法比較「手工」——用實際比賽影片跑完整分析，然後人工檢查結果。

主要看的指標：
- **球偵測率**：是不是大部分幀都有偵測到球？（目標 > 90%）
- **機器人追蹤涵蓋率**：機器人位置在多少百分比的幀有資料？
- **ID 穩定性**：一台機器人從頭到尾是不是同一個 ID？
- **射手歸因率**：進球有多少成功歸因到機器人？

也寫了一個 `test_analysis.py` 互動式測試工具，可以在影片上畫 Hub 區域然後跑分析，直接看結果。

## 11. 問題紀錄與反思

### 11.1 最大的坑：ByteTrack IoU 在 4K 下失效

這大概是我們花最多時間 debug 的問題。一開始用 ByteTrack 跑出來幾乎沒有追蹤結果，我們以為是模型問題、參數問題，調了很久。後來才想到去印 IoU 值，發現全是 0。

教訓：**不要假設現成的演算法一定適用自己的場景**。ByteTrack 在一般監控影片（720p、30fps、物體大）上很好用，但在我們的場景（4K、60fps、物體小、移動快）就完全不行。

### 11.2 訓練資料不匹配

AI 球偵測模型（近距離訓練資料）在遠距離場景失效，浪費了不少時間。AI 模型的效果取決於訓練資料跟實際場景的相似程度，差太多就不行。

HSV 反而更穩定，因為顏色不太會隨距離改變。

### 11.3 參數敏感度

4K 影片的很多參數跟 1080p 差很多：
- `MAX_BLOB_AREA`：1080p 下 10000 就夠，4K 要 50000
- `SCORE_MAX_SHOOTER_DIST`：1080p 下 300px 合理，4K 下要 500px
- 形態學核大小也需要依解析度調整

我們後來做了 RuntimeConfig + Preset 系統，可以儲存不同場地的參數。但理想上應該要能根據影片解析度自動縮放，這個還沒做到。

### 11.4 機器人追蹤仍待改善

截至最新測試（2026-02-28），HSV Bumper 模式在實際影片上追蹤機器人的效果不穩定。球偵測正常，但機器人追蹤完全失效。可能的原因：

1. HSV Bumper 參數需要針對實際場地燈光調整
2. 背景模型可能把 bumper 的色彩也過濾掉了
3. Bumper 取色模板可能沒正確傳遞給偵測器

這是目前最大的 open issue。
